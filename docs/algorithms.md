# Algorithm notes

A deeper look at how each analyzer actually works, mostly for whoever ends up extending or auditing them later. The short version of each lives in doc comments right above the relevant type in the source; this file just has more room to get into the "why" without cluttering that up.

## Error Level Analysis (`Sources/ForensicLens/Analyzers/ELAAnalyzer.swift`)

ForensicLens doesn't carry a real JPEG encoder, so ELA can't literally re-save a JPEG file the way you'd expect. What `JPEGRecompressionSimulator` does instead is perform the one lossy step that actually matters — level shift, 8x8 block DCT, quantize at the configured quality, dequantize, inverse DCT — directly against the decoded `PixelBuffer`. That's the exact operation a real encoder's lossy stage performs. Skipping entropy coding and the container format doesn't change the error signature ELA is looking for, and as a bonus the analyzer ends up working identically on every format the package can decode, not just JPEG.

The DCT itself (`DCT8x8`) is a plain, separable implementation with a precomputed cosine table. There's not much to gain from an FFT-based transform at a fixed 8x8 block size, and honestly a direct implementation is a lot easier to check by hand for correctness.

A single quantization quality is a sensitivity/noise trade-off: coarser quantization (lower quality) makes genuine edits stand out more but also makes untouched high-frequency content like edges and text noisier, and there's no one value that's right for every image. Rather than picking one, `elaQualityLevels` runs the whole recompress-and-diff pass once per configured quality (default `[70, 80, 90]`) and `ELAAnalyzer.combine` folds the resulting per-level error maps into a single map, weighted by cross-level agreement: each pixel's combined error is its max error across levels, scaled by the fraction of levels whose own error at that pixel already independently crossed `errorThreshold`. A pixel that spikes at only one quality gets scaled down toward the noise floor; a pixel that spikes at every configured quality keeps its full magnitude. That's a deliberate choice, not just noise reduction -- ordinary image content (sharp edges, fine texture) tends to interact with quantization at just one or two of the configured qualities, while a genuinely different compression history (a pasted or re-saved patch) shows up no matter which quality you recompress at, so cross-level consistency is a stronger tampering signal than the single noisiest level's raw magnitude. `errorThreshold` and `flaggedRegionFraction` then control how that combined, consistency-weighted error map turns into a small number of reported "regions": the map gets bucketed into 16x16 reporting cells, and a cell counts as "hot" once its mean combined error crosses the threshold. The trade-off for all this is cost: scanning at N quality levels means N recompression passes instead of one, so ELA's running time scales with `elaQualityLevels.count`.

## EXIF / metadata analysis (`Sources/ForensicLens/Analyzers/MetadataAnalyzer.swift`)

EXIF lives in a JPEG's `APP1` marker segment, which sits in the file header before any compressed pixel data even starts. That means this analyzer never needs a working JPEG pixel decoder — `ExifReader` just walks the JPEG's marker segments looking for `APP1` with an `Exif\0\0` preamble, then parses just enough of the embedded TIFF structure (byte order, IFD0, the Exif SubIFD) to pull five tags: Make, Model, Software, DateTime, and DateTimeOriginal/DateTimeDigitized. It's not a general TIFF library by any means; unrecognized tags and IFDs just get skipped rather than decoded.

Worth keeping in mind: every indicator this analyzer raises is a proxy, not proof. A `Software` tag naming an editor means the file passed through that editor at some point — it doesn't mean anyone used it to deceive someone. The weights in `MetadataAnalyzer.analyze` try to reflect that: a suspicious software signature and an internally impossible timestamp order carry real weight, while a missing Make/Model tag (plenty of legitimate exports have none at all) is treated as a mild nudge rather than a verdict on its own.

## Copy-move / clone detection (`Sources/ForensicLens/Analyzers/CloneDetectionAnalyzer.swift`)

The block-matching here is the classic approach to block-based copy-move detection: slide a `blockSize` window across the image at `blockStride`, reduce each block to a coarse 4x4 grid of average brightness (cheap to compute, cheap to compare), then look for pairs of blocks whose feature vectors are close together and whose positions are far enough apart that they can't just be two overlapping samples of the same patch of sky.

If there's one piece of this analyzer that matters most for precision, it's the variance filter (`minimumBlockVariance`). Flat regions — a clear sky, a studio backdrop, an out-of-focus background — are trivially "identical" to each other under pretty much any similarity metric, and without filtering them out first they'd dominate the match list and bury any real finding in noise. Skipping low-variance blocks before comparison, rather than filtering matches after the fact, also keeps the comparison step itself roughly proportional to how much actual detail is in the image.

One thing this implementation doesn't do is shift-vector voting — clustering matches by a dominant `(dx, dy)` offset, which production copy-move detectors usually add to suppress false positives from repetitive textures like brick or tile patterns. That's a reasonable thing to add later if false positives on textured photos turn out to be a real problem, but it felt like extra machinery this project didn't need just to prove the core technique out.

## Combining scores (`Sources/ForensicLens/Scoring/SuspicionScorer.swift`)

`SuspicionScorer` takes the strongest single analyzer score as the dominant signal and lets the other two add a smaller, capped amount on top when they back it up, rather than just averaging all three. A plain average would let one unambiguous finding (say, a 95 on clone detection) get diluted by two analyzers that simply had nothing to say about a small, EXIF-less BMP — and that's not really how a human reviewer would weigh the same pile of evidence anyway.

## Tiled processing for large images (`Sources/ForensicLens/Tiling`)

Everything above assumes an analyzer gets the whole decoded `PixelBuffer` in one call, and for most images it still does — tiling only kicks in once `max(width, height)` exceeds `tilingThreshold`. Above that, `TilePlan` divides the image into a grid of non-overlapping "core" rectangles that exactly partition it (no gaps, no double coverage), each expanded by a `tileOverlap`-pixel halo on every side to give windowed computations near a tile's edge real neighboring pixels instead of a synthetic replicated border. Every tile origin is kept a multiple of 8, and `tileOverlap` is required to be one too: `ELAAnalyzer` and `DoubleCompressionAnalyzer` both anchor an 8x8 DCT block grid at whatever buffer's local `(0, 0)` they're given, so keeping every tile's extraction origin 8-aligned keeps that grid in phase with the one a single, untiled pass over the whole image would use. Get that alignment wrong and a tile boundary shows up as a seam of spurious recompression error that has nothing to do with the image.

`SpatialTileMerger` is what ELA and double-compression detection actually go through: it calls each one's ordinary `analyze(_:config:)` once per tile, completely unmodified, then combines the resulting per-tile findings by taking the strongest tile's score plus a small, capped corroboration bonus from any other hot tiles — the same dominant-plus-corroboration shape `SuspicionScorer` already uses to combine different analyzers, just applied across tiles of the same one. Summing every tile's score instead would double-count a real anomaly that two overlapping tiles both happen to detect independently in their shared halo.

Clone detection can't go through `SpatialTileMerger` at all, and this is a correctness requirement rather than a stylistic one: it needs to ask whether *any* block anywhere in the image matches *any other* block, and a forger's source block and pasted copy can land in two tiles on opposite sides of a large photo. `TiledCloneDetection` instead lets every tile contribute its candidate blocks (via `CloneDetectionAnalyzer.candidateBlocks`, unmodified, just called on a tile-sized buffer instead of the whole image) into one pooled, image-global candidate list — translated into global coordinates as they're collected, and deduplicated by keeping each block only under the one tile whose core actually contains it — before `CloneDetectionAnalyzer.findMatches` ever runs, a single time, over that complete pool. Tiling only changes how the candidate list gets assembled; the search itself is exactly what a single, untiled pass would have done.

Metadata analysis isn't tiled at all — `MetadataAnalyzer` reads EXIF once out of the whole file's raw bytes, which has no spatial structure to split up, so `TilingCoordinator` always runs it as a single call regardless of whether the rest of the report is tiled.
